Does closing the modality gap help hard-negative-trained CLIP?

2. MACHINE CONSTRAINTS AND HOW THEY SHAPED THE SETUP
---------------------------------------------------------------------------
  - No GPU (no nvidia-smi). 6 physical cores / 12 threads, 14 GB RAM.
    -> Everything is inference-only on CPU. All gap shifts are applied
       AFTER encoding, so each model encodes each dataset exactly once and
       the embeddings are cached (results/embeddings/<model>/<bench>.npz).
       Every shift / noise experiment afterwards is a numpy operation that
       takes seconds.
    -> CLIP-FT training is NOT possible on this machine (needs a GPU:
       Colab / department server). See Section 8.
  - Disk: only ~18 GB free (92% full).
    -> We do not store the 6.2 GB val2014.zip (see 3c).
  - Network: ~0.3-2 MB/s to the COCO server.
  - System Python 3.12 lacks ensurepip (python3-venv not installed, no
    sudo used). -> venv created with `python3 -m venv --without-pip .venv`
    and pip bootstrapped with get-pip.py. Torch is the CPU build.


3. DATA - WHAT IS DOWNLOADED AND WHY  (scripts/download_data.sh)
---------------------------------------------------------------------------
The script is resumable: every step is skipped if its output exists, and
downloads go to *.part and are renamed only on success.

  3a. COCO 2014 caption annotations (annotations_trainval2014.zip, 241 MB)
      Only captions_train2014.json and captions_val2014.json are kept
      (instances / keypoints are not needed); the zip is deleted.
      -> data/coco/annotations/

  3b. Karpathy splits (coco_karpathy_{train,val,test}.json, BLIP format,
      from the same URLs the ARO repo uses). 113,287 / 5,000 / 5,000
      images with ~5 captions each. The ARO COCO-Order task is defined on
      the Karpathy test split, so we use the same split everywhere.
      -> data/coco/

  3c. COCO val2014 images - ONLY the 10k Karpathy val + test images.
      Karpathy val/test are drawn from val2014. Instead of downloading the
      whole 6.2 GB zip (40k images) we read the zip's central directory
      with HTTP range requests (the COCO S3 server supports them) and pull
      only the 10k needed members, 16 parallel connections
      (scripts/fetch_karpathy_images.py, uses the `remotezip` package).
      ~1.6 GB instead of 6.2 GB, nothing extra on disk. Re-runnable: images
      already on disk are skipped.
      -> data/coco/val2014/  (10,000 jpgs)
      The 2014 *train* images (13 GB) are NOT downloaded: they are only
      needed for CLIP-FT training, which happens on a GPU machine later.
      The 2017 val images (SugarCrepe) are not downloaded, as agreed.

  3d. ARO VG-Relation + VG-Attribution (Yuksekgonul et al. 2023)
      Annotation jsons + a ~1 GB image zip (a subset of GQA / Visual
      Genome), from the Google Drive IDs hard-coded in the ARO repo
      (github.com/mertyg/vision-language-models-are-bows).
      -> data/aro/

  3e. NegCLIP checkpoint (ViT-B/32), Google Drive ID from the ARO repo
      (model_zoo/__init__.py). The release is a 1.8 GB training checkpoint
      (run name "mscoco_all_neg_all_bs256_1e-6_unlocked", epoch index 4 =
      5th epoch -> batch 256, LR 1e-6; useful for matching CLIP-FT).
      It also stores optimizer / AMP-scaler state with pickled numpy
      scalars, so torch.load(weights_only=True) refuses it. Instead of
      weights_only=False (would execute arbitrary pickle code), we allow
      only the one numpy scalar type, keep the 302 model tensors and save
      them as checkpoints/negclip_state_dict.pt (~600 MB)
      (scripts/convert_negclip.py). The original .pth is then deleted to
      save disk (re-downloadable). Loads cleanly in OpenCLIP 3.3; logit
      scale 100 (same as CLIP); mean relative weight change vs CLIP 0.25%
      (max 1.0%), as expected for LR 1e-6 fine-tuning.
      -> checkpoints/negclip_state_dict.pt

  3f. NegCLIP train / valid split files (train_neg_clip.tsv,
      valid_neg_clip.tsv) from the ARO repo's temp_data/ (step 6 of the
      download script, raw.githubusercontent.com).
      -> data/negclip/
      Used for the overlap check (Section 4) and, later, to train CLIP-FT
      on EXACTLY the same images as NegCLIP (just ignoring the negatives).


4. LEAKAGE CHECK  (scripts/check_overlap.py)  - DONE
---------------------------------------------------------------------------
NegCLIP's training file contains COCO *val2014* images, i.e. it was trained
on Karpathy train + "restval". Result of the check:
    Karpathy train (113,287 imgs) & NegCLIP train : 109,468 shared
    Karpathy val   (5,000 imgs)   & NegCLIP train : 0
    Karpathy test  (5,000 imgs)   & NegCLIP train : 0
    Karpathy val   & NegCLIP valid                : 4,839 shared
=> Karpathy val and test were never trained on. Karpathy val WAS NegCLIP's
   validation set (used to pick its learning rate / checkpoint), so it is
   not perfectly "unseen", but no gradient step used it.
Decision: fit the gap vector on Karpathy val, report all evaluations on
Karpathy test (and ARO). This keeps fitting and evaluation separate.
Side note: NegCLIP's training file has ONE caption per image (109,468 rows
= 109,468 unique images). CLIP-FT must use the same file to be a fair
control.


5. CODE  (src/ and scripts/)
---------------------------------------------------------------------------
5a. Models (src/models.py)
    clip    : OpenCLIP "ViT-B-32-quickgelu", pretrained="openai"
    negclip : same architecture, weights from checkpoints/negclip.pth
    ft_*    : our fine-tuned grid (Section 8), checkpoints/<name>.pt
    Decision: QuickGELU for every model. The OpenAI weights were trained
    with QuickGELU and NegCLIP was fine-tuned from them. The ARO repo
    loads NegCLIP as plain "ViT-B-32" (standard GELU), which does not
    match training. We check this by reproducing the paper's NegCLIP ARO
    numbers. If our numbers are off, also try arch="ViT-B-32" (load_model
    has an `arch` override).

5b. Benchmarks in one format (src/data.py)
    Each benchmark = list of unique images (path, optional crop box) +
    list of unique captions + index arrays (test case -> image, test case
    -> caption options, which option is correct). This lets one cached
    embedding file serve every experiment, and de-duplicates repeated
    captions/crops (fewer encodes on CPU).
      coco_val / coco_test : Karpathy splits, ~5 captions/image, captions
                             cleaned with the BLIP/ARO pre_caption.
      vg_relation          : 23,937 cases, crop to the relation bbox,
                             [false, true] caption, group = relation name.
      vg_attribution       : 28,748 cases, same, group = attribute pair.
      coco_order           : each Karpathy-test caption vs 4 word-order
                             perturbations (shuffle nouns+adjs, shuffle
                             everything else, shuffle within trigrams,
                             shuffle trigrams) - same functions as the ARO
                             repo (spaCy + nltk).
    Decision: the ARO repo re-draws the COCO-Order perturbations at random
    on every load (no seed). We draw them once with seed 0 and cache them
    (data/aro/coco_order_test_seed0.json), so every model and every shift
    is scored on the exact same negatives.

5c. Encoding (src/embed.py)
    - Image encoding: DataLoader (4 workers), batch 128, ~25 img/s on CPU.
    - Text encoding speed-up (exact): captions are ~15 tokens but padded to
      77. CLIP's text transformer is causal and pools at the EOT token, so
      positions after the longest caption in a batch never affect the
      output. We run the same layers on only the first L positions (L =
      longest caption in the batch), with captions sorted by length.
      Verified against model.encode_text on 1,000 COCO captions: max abs
      difference 3e-7, min cosine 1.000000; speed 149 vs 31 captions/s
      (~5x).
    - Cache = L2-normalised float32 image and text matrices + logit scale +
      a fingerprint of the image/caption lists, so a changed benchmark
      triggers re-encoding instead of silently using stale embeddings.
    - Estimated encode cost per model: ~62k images/crops (~40 min) +
      ~280k captions (~30 min) => ~1.2 h per model, ~2.5 h for both.

5d. Approach 01 - gap metrics (src/gap.py: gap_metrics; scripts/measure_gap.py)
    For each model on coco_val and coco_test:
      gap_norm          ||mean(img) - mean(txt)||  (Liang et al.; 0.82 for CLIP)
      gap_norm_median   same with coordinate-wise medians
      centroid_cos      cosine between the two centroids
      *_centroid_norm   norm of each modality's centroid (near 1 = narrow cone)
      proj_*_mean/std   coordinate of each embedding along the unit gap
                        direction u = Delta/||Delta||
      var_frac_img/txt  fraction of within-modality variance along u.
                        A random direction gets 1/512 = 0.002. Close to
                        0.002 => the gap is ~orthogonal to how embeddings
                        vary (the Chowers et al. condition). This number
                        also predicts how much a shift CAN change rankings
                        (see approaches.txt, Section 4 note).
      matched_cos / unmatched_cos   mean cosine of true / random pairs
      alignment         E||x - y||^2 over matched pairs (Wang & Isola)
      uniformity_*      log E exp(-2||u - v||^2) per modality (Wang & Isola)
      linear_sep_acc    logistic-regression accuracy of image vs text
    Output: results/gap_metrics.csv and results/figures/pca_<split>.png
    (2-D PCA of both modalities, one panel per model, as in Liang Fig. 1).

5e. Approach 02 - shifts (src/gap.py: apply_shift, alpha_for_target_gap)
    Delta is fitted on coco_val and applied unchanged to every benchmark.
      mode "text": y' = Normalize(y + alpha * Delta), images untouched.
                   Moves one modality toward the other along the global gap
                   vector (the shift described for Chowers et al.).
      mode "both": x' = Normalize(x - alpha/2 * Delta),
                   y' = Normalize(y + alpha/2 * Delta)  (symmetric version of
                   Liang et al.'s shift experiment).
      alpha = 1 closes the gap before re-normalisation, alpha < 0 widens it.
      stat "mean" / "median": Delta from means or coordinate-wise medians.
      Two kinds of settings:
        alpha sweep : alpha in {-0.5, -0.25, 0, 0.25, 0.5, 0.75, 1.0}
        target gap  : for each model, solve alpha (bisection) so the
                      remaining gap on coco_val = {0.6, 0.4, 0.2, 0.1}.
                      This is the "shift by a set margin" from the proposal,
                      and lets CLIP and NegCLIP be compared at EQUAL
                      remaining gap even if their original gaps differ.
    OPEN: the exact definition of the "orthogonal shift" in Chowers et al.
    (2026) must be checked against the paper (not yet in papers/). If it
    is different (e.g. shift along the part of Delta orthogonal to the
    embedding subspace), add it as a third mode in apply_shift.

5f. Approach 04 - evaluation (src/evaluate.py; scripts/shift_eval.py)
      ARO (vg_relation, vg_attribution, coco_order):
        acc       - micro accuracy (true caption scored highest)
        macro_acc - mean over relations / attribute pairs (VG-A: pairs with
                    >= 25 cases), as reported in the ARO paper
        margin    - score(true) - best score(wrong): moves even when the
                    accuracy does not
      COCO Karpathy test retrieval: i2t / t2i Recall@1/5/10.
      Robustness: Gaussian noise of norm ~sigma added to both image and
        text embeddings after the shift, then re-normalised;
        sigma in {0, 0.25, 0.5, 1.0}, 3 seeds averaged.
    Output: results/shift_eval.csv, one row per
      model x stat x mode x setting x benchmark x sigma.
    Plots (scripts/plot_shift.py): metric vs remaining gap, one line per
      model, one column per sigma -> results/figures/shift_<mode>_<stat>.png

5g. Smoke test (200 Karpathy-test images, CLIP), already run:
      gap_norm 0.829 (Liang et al.: 0.82)  -> measurement is correct
      linear_sep_acc 1.0  (modalities perfectly separable)
      var_frac along gap: img 0.004, txt 0.008 vs random 0.002
      i2t R@1 0.905, t2i R@1 0.773 (on only 200 images, so high)
      text shift alpha 0 / 0.5 / 1.0 -> gap 0.83 / 0.42 / 0.02,
        t2i R@1 0.773 / 0.697 / 0.576, i2t R@1 0.905 / 0.875 / 0.780
      (early sign that naive closing hurts retrieval for base CLIP, as
       Liang et al. found; to be confirmed on the full 5k.)

8. GPU PACKAGE: FINE-TUNED CONTROLS (prepared, to be run on the GPU server)
---------------------------------------------------------------------------
Why: the CPU machine cannot fine-tune. The user has a GPU server, so the
control models are trained there, and the whole evaluation pipeline is
re-run there for all models.

8a. Design: a 2x2 grid instead of a single CLIP-FT control
    NegCLIP differs from CLIP in THREE ways: COCO fine-tuning, hard
    negative images (each image's 3-NN neighbour added to the batch) and
    hard negative captions. A single CLIP-FT control only removes both
    negative types at once. The 2x2 grid separates them:
        ft_plain    no hard images, no hard captions  (= CLIP-FT control)
        ft_hardimg  hard images only (batch composition only)
        ft_hardcap  hard captions only
        ft_negclip  both (our NegCLIP reproduction)
    ft_negclip vs the released negclip checks the reproduction. ft_hardimg
    vs ft_negclip isolates hard-negative CAPTIONS at an identical image-
    side batch (2N images), which is the cleanest test of "hard-negative
    training" for the research question.

8b. scripts/train_finetune.py - one-file re-implementation of the NegCLIP
    fork (github.com/vinid/neg_clip), checked line by line against its
    data.py / train.py / loss.py / main.py / scheduler.py:
      - data: data/negclip/train_neg_clip.tsv (109,468 images, 1 caption
        each; 80,041 from train2014 + 29,427 from val2014 restval).
        Per epoch, a random hard caption (from 1-6 per image) and a random
        hard image (from 3 NN) are drawn for each item, as in the fork.
      - batch layout and loss exactly as the fork:
          images = [I, I_hard]   texts = [T, T(I_hard), T_neg, T_neg(I_hard)]
          loss = (CE(img x all texts) + CE(first len(img) texts x img)) / 2
        i.e. hard captions only act as image->text negatives.
      - recipe: batch 256, 5 epochs, AdamW betas (0.9, 0.98) eps 1e-6,
        wd 0.2 except gains/biases/logit scale, cosine LR, 50 warmup steps,
        fp16 AMP + GradScaler, learnable logit scale clamped to 100,
        open_clip train transform (RandomResizedCrop scale 0.9-1.0),
        OpenAI ViT-B/32 QuickGELU init, drop_last, seeded.
      - after every epoch (and at epoch 0): COCO-val (valid_neg_clip.tsv,
        4,839 pairs) i2t/t2i R@1/5/10, ||gap||, matched cosine, logit
        scale -> runs/<run>/log.jsonl. So we also get HOW THE GAP CHANGES
        DURING FINE-TUNING for each config, for free.
      - difference from the fork: our validation uses plain 1:1 pairs
        (the fork also mixes hard images into validation). Only used for
        LR selection.
    CPU debug run done locally (batch 4, 3 steps, each config): batch
    layouts 4x4 / 8x8 / 4x8 / 8x16 = as intended; loss, optimizer,
    validation, checkpoint export, select_best and loading the result
    through src/models.py all work. (Even 3 steps at LR 1e-5 raised the
    val gap 0.84 -> 0.87-0.90.)

8c. scripts/gpu/run_sweep.py - 4 configs x LR {1e-5, 5e-6, 1e-6} x seeds,
    one job per GPU in parallel (GPUS="0 1 ..."), resumable.
    scripts/gpu/select_best.py - best LR per config by final-epoch val
    mean R@1 (as in the paper) -> checkpoints/<config>.pt; writes
    results/finetune_runs.csv (every run x epoch, incl. gap) and
    results/finetune_selection.json.
    src/models.py now loads any checkpoints/<name>.pt by name.
    src/embed.py / embed_all.py now run on GPU (fp32, TF32 off, so GPU
    and CPU embeddings agree).

8d. run_gpu.sh - the single command file (package root):
      0 venv (.venv-gpu, CUDA torch from PyPI) or PY=<existing python>
      1 GPU check, env dump (nvidia-smi, pip freeze)
      2 full COCO 2014 train + val images (scripts/gpu/prepare_coco_full.sh,
        19 GB download on the server; needs internet there)
      1b smoke test: 20 steps of ft_negclip at batch 256 (catches OOM)
      3 leakage check   4 sweep   5 LR selection
      6 encode all benchmarks with clip, negclip, ft_plain, ft_hardimg,
        ft_hardcap, ft_negclip
      7 measure_gap, shift_eval, plot_shift for all 6 models
      8 results_gpu.tar.gz (csvs, figures, run logs, env info, and the
        embeddings unless INCLUDE_EMB=0; ~3 GB with embeddings - they let
        us redo any shift analysis locally on CPU without the GPU)
    Options: GPUS, LRS, SEEDS, PY, INCLUDE_EMB.
    Rough cost: 12 runs x 5 epochs of 109k pairs at ViT-B/32 -> minutes
    per epoch on a modern GPU; ~1-3 h for the sweep on one GPU.

8e. scripts/make_gpu_package.sh -> dist/cs725_gpu_package.zip (3.0 GB):
    code, all local data (10k COCO images, ARO, annotations, Karpathy and
    NegCLIP splits, COCO-Order cache), NegCLIP weights. Zip integrity
    tested. Not included: COCO train2014 / rest of val2014 (downloaded on
    the server), our CPU embeddings (re-computed on GPU = cross-check).
    torch removed from requirements.txt (installed per machine).
    Rebuild the zip after any code change.

              Caveat: "relative to clean" robustness flatters fully-closed
              settings because their clean accuracy is already near chance
              (COCO-Order chance 0.2, VG 0.5) - compare absolute numbers.

              text vs both modes, mean vs median Delta: same shape; text-only
              shift hurts less than the symmetric one at equal remaining gap
              (e.g. negclip COCO-Order at gap 0.4: text 0.694, both 0.627);
              median vs mean differ by <= 0.01.

              WHY THE SHIFT CHANGES IMAGE->TEXT RANKINGS (approaches.txt
              Section 4 predicted it could only act through re-normalisation):
                - shift WITHOUT re-normalisation: accuracy exactly unchanged
                  (clip COCO-Order 0.472 -> 0.472, negclip 0.825 -> 0.825).
                - WITH re-normalisation, score' = (x.y + a x.Delta)/||y + a Delta||;
                  x.Delta is a large positive constant, and ||y + a Delta||
                  is smaller for captions further on the text side, so those
                  captions get boosted.
                - Word-shuffled COCO-Order negatives sit further on the text
                  side than the true caption: in 74% of cases for clip and
                  88% for negclip. Closing the gap therefore favours the
                  shuffled captions -> COCO-Order collapses.
                - VG-Relation negatives (grammatical subject/object swaps)
                  have the same projection as the true caption (~50/50), so
                  VG-R is barely affected.
              => The gap direction partly encodes caption "naturalness",
                 and hard-negative training strengthens that (74% -> 88%).
              Idea for next round: a re-normalisation-free (or exactly
              orthogonal) shift as a control that keeps i2t rankings fixed.
